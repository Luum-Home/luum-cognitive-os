## Decision
Introduce three components to promote ADR-033's event schema from a write-only sink to a live, subscribable stream: (1) `scripts/cos_executor.py`, a PID-locked background daemon started at SessionStart that subscribes to Valkey pattern `cos:agent:*:*` (or tails the file-fallback JSONL) and re-publishes normalized live events on `cos:canonical:live`, flipping `ORCHESTRATOR_MODE=executor` via a state file; (2) `scripts/cos_watch.py`, a TUI consumer (`cos-watch <agent_id>` / `--latest`) showing elapsed time, token usage, tool count, last 5 PROGRESS markers, and status, with plain-text fallback and graceful degradation to FallbackBus tailing; (3) a POC real-time streaming adapter for Aider (`lib/harness_adapter/aider_streaming.py`) using portable file-position polling (no inotify dependency). New canonical event types `ToolUseStart`/`ToolUseEnd`/`ProgressMarker` extend (not replace) ADR-033's aggregated `ToolUse` event, preserving backward compatibility for existing consumers.

## Why
ADR-033 solved "can I analyze a session after it finished" but not "can I watch a live agent the way Claude Code's built-in agent panel lets you" — and specifically not in a harness-agnostic way. The daemon+pub/sub architecture was chosen over three rejected alternatives: (A) each consumer polling JSONL directly — rejected because every consumer (TUI, cost dashboard, MLflow bridge) would reimplement tailing/rotation, causing N² fan-out; (B) scraping the Claude Code UI via accessibility API/TTY — rejected as fragile across versions and harness-specific, violating the ADR-033 harness-agnostic goal; (D) embedding TUI logic inside every harness adapter — rejected because it explodes adapter complexity and couples transport to presentation.

## Consequences
Positive (per rollout plan): any consumer subscribes to one channel instead of N harness-specific ones; new harnesses only need to implement `HarnessAdapter.stream_events()` to get live UX for free; the banner's "Executor OK" becomes a real, verifiable health signal instead of permanently off. Negative: one more background process to observe (mitigated by PID-file + heartbeat into `so-vitals.jsonl`); adapter authors must decide post-hoc vs live semantics (resolved by emitting both, with the daemon de-duplicating by `(agent_id, tool_name, started_at)`). Risks: Valkey outage (TUI falls back to FallbackBus tailing, daemon resumes on recovery), runaway event rate (daemon enforces `MAX_EVENTS_PER_SEC = 50`, drops with a WARN log), and multiple sessions on one project sharing a single per-project-dir daemon (idempotent by design, not per-session).

## Status & current state
Status: Proposed, `implementation_status: planned` — this is a design/roadmap ADR, not yet built. Rollout is staged W1 (this ADR: schema + daemon + TUI + Aider POC + 3 tests, gated on CI green and banner flip) through W4 (soft-deprecate post-hoc-only mode). Feature flag `runtime.live_streaming.enabled` defaults true in reconstruction/stabilization phases, false in production/maintenance until W3 is proven. Acceptance criteria are test-anchored but unverified as of this synthesis (no implementation_files listed in frontmatter).
