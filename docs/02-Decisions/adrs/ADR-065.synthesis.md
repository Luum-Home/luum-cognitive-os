## Decision
Create a new SO-only skill `/radar-update <url-or-file> [--apply]` that delegates per-repo evaluation entirely to the existing `/repo-scout` pipeline (no new DeepWiki fetch, scoring, or license-detection logic) and adds only the missing merge step. The load-bearing contract is an auto-owned vs human-owned field taxonomy: fields like `stars`, `last_commit`, `license`, `score`, and `classification` are stored as machine-parseable YAML frontmatter per entry and rewritten every run, while `usage_examples`, `adoption_notes`, `gotchas`, and `linked_adrs` are free-form markdown body content the merge engine must never touch. The merge algorithm does exact-match-by-`repo`-field frontmatter rewrite, fuzzy-match warnings for near-misses, and alphabetical inserts for new entries; classification shifts (e.g. a relicense pushing ADOPT to REJECT) move the entry between documents while preserving the human-owned body. Dry-run (unified diff) is the default; `--apply` writes files but never commits — that stays an explicit human step.

## Why
Per-repo evaluation already existed via `/repo-scout` v2.0.1 (10-step pipeline, Engram caching, classification, batch input parsing) — what was missing was purely the fold-into-canonical-docs step. ADR-064 had just made the OS harness-agnostic, and the radar is the SO's public marketing face (linked from the README), so keeping it fresh mattered; closing the curation gap was framed as turning "we evaluated 30 repos this sprint" into a 1-command radar refresh.

## Consequences
Positive: curation scales from manual copy-paste to "20 URLs -> 1 dry-run -> 1 review -> 1 apply"; human annotations are preserved by contract (auto vs human field split) rather than by hope; re-running on existing entries surfaces drift (stale licenses, archived repos, score drops) directly in the diff; CHANGELOG entries make radar movement auditable per release. Negative: diff-merge conflicts are possible if a human edits an entry while a batch is mid-flight (mitigated by re-reading the doc at `--apply` time and aborting on frontmatter change since the dry-run); the radar doc format becomes load-bearing, so any future reformat needs a migration script in the same PR; existing readable entries get YAML frontmatter prepended as one-time cosmetic clutter.

## Status & current state
Proposed 2026-04-24, `implementation_status: planned` — none of the three phases (skill + merge engine + dry-run; `--apply` + CHANGELOG side-effect; test coverage) had landed as of this ADR. Honest cost estimate in the ADR: roughly 3 sessions for a usable v1, not counting a separate migration PR to backfill YAML frontmatter onto existing radar entries that currently lack it. Explicitly deferred/open: how to resolve conflicts when human curation prose disagrees with a fresh auto-classification (leaning toward a human-owned `classification_override` field, deferred to first real conflict), and whether a periodic `--refresh` cron mode is worth the CHANGELOG noise (deferred until ~60 radar entries exist, versus ~26 at drafting time).
