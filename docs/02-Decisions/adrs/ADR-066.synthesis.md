## Decision
This is a design-only ADR (no code rewritten) that codifies an explicit role matrix for the three in-tree languages — bash for event handlers/hooks/thin glue (rejecting anything with >30-line awk/sed parsing or state machines), Python for orchestration/parsing/all tests (rejecting anything latency-critical <50ms cold-start or single-binary end-user distribution), and Go for end-user-distributed CLI tools only (`cos`, `cos-test`; rejecting any internal orchestration or test helpers). It also ratifies per-language naming conventions (kebab-case bash, snake_case Python, camelCase/PascalCase Go) and sets **numeric** migration triggers: bash→Python only when a script exceeds 200 lines AND has non-trivial JSON parsing or nested-conditional depth >3; Python→Go only when distributed as an end-user binary that would otherwise require the user to manage a Python environment. Bash hooks are explicitly forbidden from ever migrating to Python regardless of length, due to per-hook interpreter startup cost multiplied across ~154 hooks per session.

## Why
The repository had grown polyglot (154 bash hooks, ~250 Python modules with ~10,500 tests, 2 Go CLI tools) with no explicit policy, and the absence of policy was itself the root cause of repeated drift: the 35 hyphenated Python filenames had silently leaked bash's naming convention across the language boundary; the 18-second hook-chain incident (engram topic `perf/hook-chain-rca-2026-04-24`) came from ad-hoc subprocess forking instead of a defined bash↔Python boundary contract; and the missing hook-directory symlink came from an undocumented package/global contract. The operator explicitly asked whether spanning Bash/Python/Go was acceptable and requested this ADR in response — with an explicit non-goal of rewriting anything, only documenting the policy so future drift is caught by an audit test rather than discovered via a production latency incident.

## Consequences
Positive: drift like the 35-hyphenated-script incident gets caught by audit tests before landing; contributors get a single decision table ("is this hook, helper, or distributed CLI?"); migration triggers are numeric (>200 lines, depth >3) rather than a "vibe," so reviewers can disagree on a number but not a feeling; the 18s incident now has a documented mitigation path (decompose bash, or call a Python helper once instead of forking N times). Negative: the 3x-language onboarding cost persists and is explicitly accepted as the cost of specialization, not reduced; the bash and Go naming audit tests are not yet written, so those two rows are enforced by code review only until Phase 1 ships.

## Status & current state
Status: `proposed`, `implementation_status: planned`. Only the Python naming enforcement landed concretely the same day (`rules/python-naming.md` + `tests/audit/test_python_naming.py`, both already shipped in a commit-pair with this ADR). Everything else — bash naming audit tests, Go `gofmt -l`/`go vet` audit tests, the bash↔Python JSON/exit-code/env-var boundary contract enforcement, and any migration of the flagged `scripts/cos-init.sh` candidate (300+ lines, meets two of three bash→Python triggers) — is explicitly flagged as a Phase 1 follow-up, not committed work. No files were renamed, moved, or rewritten by this ADR itself.
