## Decision
Implement a local peer-card model as an Engram observation (type `peer-card`, scope `personal`, topic_key `user/peer-card`, upserted on update) holding structured JSON: name, role, preferences, communication_patterns, domain_expertise, and a capped rolling window of recent_topics (default 20 entries). Phase 1 retrieval is explicitly no-embeddings / FTS5-only via `mem_search`/`mem_get_observation` — semantic embedding search (candidate: `sqlite-vec`, rejected: `sentence-transformers` for dependency weight) is deferred to Phase 2 until a concrete retrieval gap is observed. The `user-prompt-capture` hook writes updates event-driven (not per-prompt): high-confidence signals (explicit "from now on"/"I prefer"/"call me" statements, direct memory corrections, stable identity/role facts) write immediately; medium-confidence signals (recurring language choice, repeated style feedback) are buffered and consolidated at session end; one-off task constraints, transient mood, secrets, credentials, and project-specific facts must never update the peer card. A `/peer-card` command exposes `read`, `edit <instruction>` (proposes a JSON patch, confirms unless immediate update requested), `forget <field-or-fact>`, and `explain` (shows provenance or states its absence).

## Why
COS's local-first architecture rules out a live Honcho service dependency (no internet-independent state) and an SDK addition would violate the minimal-dependency philosophy while introducing a managed Honcho API-key credential. The peer-card concept itself (Honcho's `profile` tool, MIT-licensed source at `.claude/plugins/hermes-agent/plugins/memory/honcho/__init__.py`) is straightforwardly reimplementable on Engram, which COS already uses as its persistent memory layer — making this a clean MIT-derived replacement rather than a vendor dependency.

## Consequences
Positive: no external service dependency, peer card persists fully offline; MIT-clean reimplementation reusing existing Engram infrastructure with no new service; FTS5 keyword search covers the majority of `honcho_search` use cases without an embedding stack. Negative/trade-offs: no dialectic reasoning in Phase 1 (Honcho's LLM-synthesized answers from stored memory require an agent call — higher latency/token cost, deferred); no cross-session semantic drift detection (relies on agent judgment during updates instead of ML-based tracking); FTS5-only retrieval may miss paraphrased/conceptually related memories until a concrete gap justifies Phase 2; event-driven writes require careful signal filtering to avoid noisy/creepy updates; free-text `/peer-card edit` requires showing a minimal patch before writing unless the user explicitly requests immediate update.

## Status & current state
Accepted, `implementation_status: partial` — frontmatter `partial_remaining` states Phase 2 (embedding-based semantic search) is "deferred until a concrete retrieval gap is observed," so it remains explicitly out of scope until then. Phase 1 architecture, update-cadence rules, and `/peer-card` UX are all resolved (no open blocking questions), so implementation of Phase 1 was unblocked at acceptance.
