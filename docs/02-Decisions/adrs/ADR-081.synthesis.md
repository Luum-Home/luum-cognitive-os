## Decision
Implement `lib/harness_adapter/codex.py` satisfying the same `HarnessAdapter` ABC as `claude_code.py`: parses Codex hook stdin, maps native events to canonical names (SessionStart→session_start, UserPromptSubmit→user_prompt_submit, PreToolUse/PostToolUse [Bash only]→pre_tool_use/post_tool_use, Stop→session_end), emits `ParseError` with `reason="codex_tool_coverage_gap"` for non-Bash tool events rather than silently skipping, and exposes a `SUPPORTED_EVENTS` frozenset. Adds a `codex` entry to `manifests/harness-driver-capabilities.yaml` honestly documenting v0.124.0 constraints (no PreCompact, no native scheduling). Plans to generate `.codex/hooks.json` from a single source of truth via `scripts/_lib/settings-driver-codex.sh` (deferrable with explicit tracking). Requires unit tests mirroring `test_harness_adapter_claude_code.py` and a parameterized integration test asserting byte-identical canonical events across `(claude_code, codex)` adapters. Preceded by a mandatory 30-minute spike to capture real Codex hook stdin payloads before building the adapter against assumed shapes.

## Why
Codex v0.124.0 fires `PreToolUse`/`PostToolUse` only for the Bash tool (a Codex limitation, not a COS design flaw) — documented honestly rather than papered over with a brittle polling/syscall-tracing workaround (explicitly rejected). This ADR is the first accepted slice moving Codex from "projected driver" to canonical harness adapter, unblocking ADR-064's exit condition (needs "at least one non-CC harness produces byte-identical canonical events for a reference skill") and ADR-080 Tier 1's `context_compressor` design, which assumes a working Codex event surface.

## Consequences
Positive: unblocks ADR-064 and ADR-080 Tier 1; eliminates the 2x hand-maintenance edit burden for `.codex/hooks.json`; forces an honest feature-availability matrix (Claude Code-only features made explicit); stress-tests the ADR-033 `HarnessAdapter` abstraction early with a second, materially different harness. Negative: real engineering work (~1-2 sonnet sessions); mocking Codex's stdin contract faithfully for integration tests is non-trivial; some COS hooks remain permanently Claude Code-only, creating a documented two-tier system. Risk: adapter must track Codex's evolving hook schema (version_baseline canary); `bash_only` coverage could mislead hook authors expecting full parity.

## Status & current state
Accepted; implementation_status: partial. Shipped 2026-04-30 (commit `9062829`): `lib/harness_adapter/codex.py` normalizes live Codex Desktop session rows and hook stdin into canonical events; `dispatch.py` registers `CodexAdapter` before Claude Code; `internal/provider/codex.go` maps events and reports `codex_tool_coverage_gap`; `manifests/harness-driver-capabilities.yaml` records Codex v0.126.0-alpha.8 as baseline. `test_harness_agnostic_skill_run.py` shipped, 4/4 tests passing, satisfying ADR-064's gate. Deferred/open gaps: `scripts/_lib/settings-driver-codex.sh` does not exist — `.codex/hooks.json` remains hand-maintained without a `DO NOT EDIT` header (tracked as ADR-057/ADR-064 follow-up, severity MEDIUM); `dispatch.handle_event` does not consult `SUPPORTED_EVENTS` before routing (severity LOW, defence-in-depth gap only, since `parse_event` handles unknowns gracefully).
