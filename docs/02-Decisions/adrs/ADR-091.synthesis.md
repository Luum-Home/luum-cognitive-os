## Decision
Accept a two-mode runtime taxonomy — (1) local harness runtime (current mode) and (2) headless runtime (future mode accepting tasks from queues/CI/tickets without an interactive harness) — explicitly superseding ADR-084's three-mode taxonomy for this contract. Clustered/Kubernetes operation is scoped as a future deployment surface under headless runtime, and Cognitive OS must not claim cluster-readiness until a long list of concrete requirements are implemented and verified: a runtime server/worker mode (`cos worker`, `cos run-task`, `cos repair`, `cos queue-drain`), durable shared state (Valkey/Postgres/object storage with explicit degradation rules), per-task workspace isolation (worktree/container/ephemeral volume with rollback), unattended solo-cloud controls (task leasing, crash-safe idempotent resume, no direct publication to main, remote kill switch), a queue/scheduler with dead-letter handling, capability-centric provider routing, a security model (per-task permissions, secrets via env/secret manager, audit trail), observability (traces, repair success rate, cost/latency), and Kubernetes packaging (Helm/manifests, readiness/liveness checks) before using language like "Kubernetes-native autonomous repair cluster."

## Why
The repository already contains necessary-but-insufficient foundations for this direction (lifecycle hooks, Engram-backed memory, JSONL metrics, task/session state, queues, rate limiting, repair loops, dispatcher/provider layer, doctor scripts, increasing separation between `.cognitive-os/` runtime state and driver projections). The solo-maintainer-swarm persona strengthens the case: a single operator deliberately running COS unattended in the cloud turns primitives that feel heavy for a one-session laptop workflow (leases, idempotency, protected landing, audit trails, human-approval gates) into required controls, because the missing human-in-the-loop increases blast radius.

## Consequences
- Positive: provides a clear growth path beyond Claude/Codex local hooks, aligned with the durable-product master plan; prevents early vendor lock-in by requiring capability-centric routing; makes EC2/container/pod execution a planned target rather than an accidental script side effect.
- Negative: risk of over-engineering if headless features invade the local default path; shared-state and cluster features add operational complexity; security expectations rise sharply once the runtime can mutate repositories without an interactive developer; product messaging must stay honest while the runtime remains local-first.

## Status & current state
Accepted as direction, explicitly "not yet implemented as a production cluster." implementation_status: partial. Guardrails require local default stay lightweight, headless/clustered features remain opt-in until mature, `.cognitive-os/` remains canonical runtime state, and every new headless claim needs a runnable proof path or test. Non-goals explicitly stated: COS is not yet a Kubernetes-native autonomous repair cluster, and is not yet a fully unattended cloud operator until Phase 1/2 crash recovery, lease, safe-mode, artifact, and publication gates are proven.
