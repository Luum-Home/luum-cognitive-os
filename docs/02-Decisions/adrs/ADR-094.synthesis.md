## Decision
Three layered defenses, registered in both `default` and `full` profiles as safety-critical: Mechanism A, `hooks/pre-agent-snapshot.sh` (PreToolUse:Agent) runs `git stash push --include-untracked --keep-index -m "auto-pre-agent-<AGENT_ID>"` before every agent launch if the tree is dirty, recording the stash ref to session JSON and `agent-snapshots.jsonl`; always exits 0 (advisory, never blocks). Mechanism B, `hooks/post-agent-verify.sh` (PostToolUse:Agent) diffs the working tree against the saved stash, compares touched files to the agent's declared TOUCH scope, and auto-restores (`git checkout stash@{N} -- <path>`) any out-of-scope write while logging the violation and alerting to stderr — if no TOUCH scope was recorded, it warns but does NOT auto-restore, since guessing scope is riskier than restoring legitimate work by mistake. Mechanism C, `hooks/destructive-git-blocker.sh` (PreToolUse:Bash) pattern-matches `git stash pop/drop/apply`, `reset --hard`, `checkout --`, `clean -f`, `restore`, `revert`, `worktree`: blocks (exit 1) when `CLAUDE_AGENT_ID` is set (sub-agent context), but only warns-and-allows for the orchestrator/direct user, since a human deliberately invoking git is assumed to know what they're doing.

## Why
Root cause was explicitly not agent ignorance but "interpretation drift": the scope guard already existed as prompt text ("TOUCH only... DO NOT TOUCH..."), but an agent told to "verify Y is clean" can reach for `git stash` or `git checkout --` as a reasonable-seeming verification tool without realizing the side effects cross the scope-guard line, and none of these destructive commands produce a meaningful warning — they exit 0 with terse output, so the agent reports "done" and nothing catches the silent revert. The ADR explicitly rejects "just educate agents better" because the guard was already in every prompt and agents still triggered the failure; enforcement at the Bash tool layer was judged the only reliable defense.

## Consequences
Positive: eliminates an estimated ~95% of the "agent destroyed working tree" failure mode from Sprint 2a; agents that reach for a blocked destructive op get an explicit, self-correcting error message instead of silent damage; out-of-scope writes are automatically reverted with a visible alert. Negative/cost: every agent launch consumes a stash slot (stashes currently accumulate — pruning is manual via `git stash list | grep auto-pre-agent`, described as future work); ~50ms added per agent completion for the post-agent diff; ~30-100ms added per agent launch when the tree is dirty. Residual gap: the ~5% of destructive-tree damage reachable outside `git` (e.g. direct `rm -rf`) is out of scope here and tracked as separate follow-up work (`destructive-rm-blocker.sh`).

## Status & current state
Accepted (2026-04-16), implementation_status PARTIAL per frontmatter, with the explicit remaining gap being the `rm -rf`-class destructive operations not covered by this ADR's git-focused mechanisms. All three mechanisms (A, B, C) are described as implemented with 14 behavioral tests across `test_pre_agent_snapshot.py`, `test_post_agent_verify.py`, `test_destructive_git_blocker.py` covering snapshot create/skip, metadata writes, violation detection, restoration, and all five destructive-op families.
