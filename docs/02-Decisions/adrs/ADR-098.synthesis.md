## Decision
Add a file-level edit-coordination layer built on the same atomic-mkdir primitive as ADR-089's git-coop, with a deliberately rich (~15-field) YAML lock schema so other sub-agents can introspect and self-select a response without asking the holder. Components: `scripts/edit-coop.sh` (acquire/release/check/status/heartbeat/release-mine, PID-based stale detection, idempotent re-acquire), `hooks/edit-lock-pre-tool.sh` (PreToolUse[Edit|Write] enforcement, exit 2 with structured conflict info — NOT yet registered, Phase A ships opt-in only), `skills/coordination-status` (read-only introspection before planning), and a response template offering 4 named options on conflict: PARK (save edit as JSON sidecar, work elsewhere), READ-ONLY, NEGOTIATE (write request to a per-pair YAML, holder reads on heartbeat), or ESCALATE (`COS_BYPASS_EDIT_LOCK=1`, audit-logged, reserved for `critical-bugfix` priority). TTL defaults to 1800s (longer than git-coop's 300s since edits run longer than git ops); the layer complements worktrees rather than replacing them — with a worktree, file conflicts become physically impossible between sessions and the lock layer becomes belt-and-suspenders for sub-agents/hooks within one session.

## Why
ADR-089 solved git-index-level coordination (two sessions can't both `git commit --only` the same file concurrently) but never addressed working-tree edit collisions — a structurally different failure mode. The 2026-04-30 incident combined three gaps at once: no file-level lock, no introspection registry (Session B had no visible way to know A was mid-edit), and no defined response protocol even if a conflict were detected.

## Consequences
Positive: the exact 2026-04-30 failure mode (concurrent edits silently overwriting each other) is structurally prevented when both sides honor the layer; sub-agents become coordination-aware by reading purpose/related_adr/intent from the lock YAML instead of retrying/failing blindly; shares idiom/TTL/stale model with ADR-089 so contributors learning one understand the other. Negative: ~30ms latency per Edit/Write tool call for the PreToolUse hook (mkdir + sed + JSON parse) — bounded, within latency-budget rules; a session that forks/exits uncleanly without releasing leaks a lock until TTL fires (30 min), mitigated by a recommended (separately registered) `release-mine` session-end hook; negotiation is advisory only — a holder may ignore requests, which is intentional (automated mediation/CRDT was explicitly rejected as over-engineering at current 2-4 concurrent-agent volume, revisit if concurrency crosses 10 or blocked-edit rate exceeds 5%).

## Status & current state
Accepted, `implementation_status: partial` — explicit remaining scope per frontmatter: a lock-contention metric showing >5% blocked-edit rate (or concurrent-agent count crossing 10) is the defined re-evaluation trigger for revisiting CRDT/OT, and that metric does not yet exist. Rollout is explicitly phased: Phase A (shipped) — primitive + skill + template + 12 unit tests, hook NOT registered (opt-in, sub-agents call edit-coop directly); Phase B (next minor) — register `edit-lock-pre-tool.sh` as a standard PreToolUse[Edit|Write] hook after a release cycle shows zero false positives; Phase C (when needed) — wire `release-mine` into the session-end hook chain so lock leaks are bounded by session end rather than TTL.
