## Decision
Four coordinated fixes to the task tracker lifecycle. Fix 1: defer `in_progress` until the agent process actually starts — `hooks/agent-prelaunch.sh` and `hooks/_lib/task_bridge.py::register()` now write `status: "pending"` at PreToolUse time with a `requested_at` timestamp; `dispatch_gate_check.py` already only counted `in_progress`, so pending records correctly consume no dispatch slots. Fix 2: PID capture — `scripts/write_context_marker.py::_claim_pending_task()` claims the most recent matching `pending` record (by `CLAUDE_TOOL_USE_ID`, falling back to most-recently-created) and sets `status=in_progress`, `pid=os.getpid()`, best-effort with all errors swallowed. Fix 3: zombie reaper extension — `scripts/so-reaper.sh` gains an `fcntl`-locked sweep that marks (never kills) dead-PID `in_progress` records as `cancelled-zombie` and stale (>30min) `pid=null` `pending` records as `cancelled-stale`; a further watermark sweep marks tasks `completed-by-watermark` when their `expectedOutputs` exist on disk or their description shares ≥3 content tokens with a recent commit subject. Fix 4: `lib/queue_drainer.py` gains `_sync_active_tasks()`, `cancel_queued()`, and an updated `mark_dispatched()` to keep `dispatch-queue.json` and `active-tasks.json` synchronized.

## Why
Four independent bugs compounded: (1) premature `in_progress` writes created unkillable phantom dispatch slots on any agent-start failure; (2) `pid` was always `null` even for completed tasks, making `agent_health_monitor.py`'s dead-PID detection logically unreachable dead code; (3) the zombie reaper only processed PIDs already in `lib.process_registry`, so `pid=null` records were invisible to it and accumulated without cleanup; (4) `dispatch-queue.json` and `active-tasks.json` were unsynchronized independent state files, so cancelling or dispatching a queue item silently left the corresponding `active-tasks.json` record stale.

## Consequences
Positive: dispatch-gate accuracy is restored (only genuinely running agents consume slots); queue draining is unblocked (stale records no longer cause permanent saturation); PID-based liveness checks in `agent_health_monitor._classify_task()` become reachable now that subagents capture PIDs; `active-tasks.json` stays consistent with `dispatch-queue.json` across cancel/dispatch. Negative: PID capture depends on the subagent's own preamble cooperation — if a subagent bypasses the preamble, PID stays null and the record falls back to the 30-minute stale-age cleanup; the most-recent-pending fallback matching is heuristic and can misattribute PIDs under burst launches (>1 agent/second) until harness-level `CLAUDE_TOOL_USE_ID` injection lands; the 30-minute stale threshold means a crashed subagent's record can persist up to 30 minutes before cleanup.

## Status & current state
Accepted, partial. `partial_remaining` per the ADR frontmatter: "Queue draining unblocked: stale records no longer cause permanent saturation" is noted as the specific remaining/closing signal. New test suite `tests/unit/test_task_tracker_lifecycle.py` (14 tests, all passing) covers the fixes; `tests/unit/test_task_bridge.py` was updated to assert `"pending"` status.
