## Decision
Define a bilateral claim verification contract: high-stakes claim verbs (`archived`, `deleted`, `removed`, `wired`, `integrated`, `registered`, `done`, `closed`, `migrated`, `tested`, `verified`, `claimed`) each have an optimistic partial form (insufficient) and a required bilateral proof (the necessary inverse). E.g., `archived` requires archive-present AND original-absent AND no config references — not just archive-present. Plan file `[x]` checkboxes must attach an inline `(verified: <command> → <output>)` record; bare `[x]` is treated as unverified. The orchestrator (not the sub-agent) is the final gate: on receiving a high-stakes claim, it must independently re-run the bilateral proof command before committing, marking `[x]`, or accepting `completed` status.

## Why
Sub-agents naturally produce the optimistic partial ("present" half) of a two-sided predicate and report the whole predicate as true — this is a structural failure mode, not a one-off mistake, so the fix must be an orchestrator-owned gate rather than relying on sub-agent self-verification.

## Consequences
Positive: false-done claims become structurally harder since bilateral proof is required, not optional; plan files carry their own verification audit trail; orchestrators get a defined self-check protocol instead of trusting TRUST_REPORT scores alone; domain-specific helpers (e.g., `verify-archived.sh`) standardize what "bilateral" means per claim type. Negative: existing `[x]` entries without `(verified:)` are technically non-conformant (no backfill, forward-only); orchestrator self-check adds ~2-5 commands of latency per high-stakes claim; helpers must be maintained as paths/config evolve. Neutral: TRUST_REPORT scoring is unaffected — this is an orthogonal check.
