## Decision
Every COS runtime surface (local maintainer session, cloud worker, ephemeral sandbox) must use credentials supplied by that surface's own caller — never forwarded from an outer context, banning patterns like `export ANTHROPIC_API_KEY="$ANTHROPIC_API_KEY"` propagated into a worker launch. Three billing postures are defined: `byok-maintainer` (personal account, local harness only, cannot be promoted beyond `advisory` lifecycle state), `byok-project` (project-scoped keys, cloud workers/CI), and `proxied` (gateway-handled billing, all surfaces). Flow contracts (extending ADR-138) must declare `credential_source`, `billing_identity`, and `provider_capabilities`; undeclared capability calls are logged as contract violations. Provider identifiers in scripts/configs must use generic role-based names (`LLM_PRIMARY_API_KEY`, not `ANTHROPIC_API_KEY`) with vendor names allowed only in ADR prose, telemetry fields, and CI secret-store names.

## Why
Three converging problems named explicitly: credential leakage (ambient-env inheritance exposes personal accounts to logs/crash-dumps/sandbox surfaces), billing opacity (cloud usage accrues to the maintainer's account with no per-flow cost attribution, since `llm-dispatch.jsonl` can't correlate charges across accounts), and an unaddressed adjacent question to the existing license-policy rule (§10) — which providers COS can route to under BYOK versus proxied/managed billing, and whether that distinction changes for cloud workers versus local harness usage.

## Consequences
Positive: cloud workers structurally cannot accidentally expose maintainer credentials — the caller-supplied model is checkable at flow-registration time; per-flow cost attribution becomes structurally required (every LLM call appends a row to `.cognitive-os/runtime/agent-audit-trail.jsonl` with `billing_identity`); license posture for provider libraries is explicit and auditable. Negative: flows currently inheriting ambient credentials need a one-time migration to declare `credential_source` explicitly; generic env-var names add a mapping layer that must be documented per deploy target. Named cost of not adopting: the first cloud worker flow would leak maintainer credentials into sandbox logs with no structural guarantee, only convention, and cross-flow cost analysis would be impossible without `billing_identity`.

## Status & current state
Accepted and implemented. Verified in place: `manifests/flow-contract-schema.yaml` requires the three new fields; `scripts/cos-flow-register.sh`/`cos_flow_register.py` reject flows missing them; `docker/cos-worker/docker-compose.yml` uses generic `LLM_PRIMARY_API_KEY`/`LLM_FALLBACK_API_KEY` names; `scripts/cos-engram-cloud-enroll` uses project-scoped Engram variables without printing token values; both are validated by `tests/audit/test_flow_contract_schema.py` and `tests/audit/test_adr_139_141_142_cloud_surfaces.py`.
