## Decision
Cloud workers needing COS as an embedded runtime MUST be launchable via a Docker Compose stack (`docker/cos-worker/docker-compose.yml`) containing a `cos-worker` service plus an optional `cos-engram-proxy` sidecar (ADR-141), using bind mounts (not baked-in project state) and env-var-only configuration (no shell profile sourcing). It targets Linux primarily, macOS for developer testing, and Windows via WSL2 for CI compatibility (native Windows Docker without WSL2 is explicitly unsupported — the hook layer is Bash-based and a native Windows shell would need a separate implementation not yet warranted). Base image is `python:3.11-slim`, following the existing ADR-048 image-freshness policy; no image is published to a registry by this ADR. Optional services (Postgres, Valkey, Engram daemon per ADR-060) remain optional via Compose profiles. This is a cloud-worker surface only — the maintainer's local pip-install path is explicitly unchanged, and no docker-compose.yml replaces it at the repo root.

## Why
None of the developer-machine assumptions baked into the current install path hold in ephemeral/CI environments: no guaranteed shell profile, no `~/.claude/`, no running Engram daemon, no guaranteed outbound PyPI access. ADR-048 already handled Docker image freshness for optional services (Postgres/Valkey/Engram) but never addressed COS itself as a containerized runtime — this ADR closes that specific gap so the `cos-cloud-worker-bootstrap.sh` entry point (named in ADR-137/the bootstrap plan) has a concrete, testable deployment target instead of remaining aspirational.

## Consequences
Positive: cloud workers become launchable on any Docker-capable platform without assuming developer tooling; the Compose stack doubles as a mechanical portability test surface for ADR-064 (harness-agnostic) coverage — a container that boots COS and runs hooks proves portability directly; optional services stay opt-in per flow via Compose profiles. Negative: Docker becomes an additional operational dependency — operators in locked-down CI environments without Docker must fall back to a direct pip install in their own container image; Windows WSL2 bind mounts have known latency characteristics on large workspaces, so I/O-heavy flows should benchmark before committing to Compose on Windows. Cost of not doing this: every cloud-worker flow would invent its own container assumptions ad hoc, becoming a de-facto (undocumented) standard, leaving `bootstrap-portability.md` aspirational rather than gate-enforced.

## Status & current state
Accepted, `implementation_status: implemented`. Implemented artifacts: `docker/cos-worker/docker-compose.yml` (cos-worker service, account-agnostic provider-key env names per ADR-139, workspace bind mount, optional cos-engram-proxy profile), `docker/cos-worker/Dockerfile` (python:3.11-slim, Bash/Git, no shell-profile dependency), `docker/cos-worker/entrypoint.sh` (self-test boot path running a hook smoke test and writing `agent-audit-trail.jsonl`), and `scripts/cos-cloud-worker-bootstrap.sh` (thin Compose wrapper for config/self-test/up/down). Validated by `tests/audit/test_adr_140_cos_worker_compose.py`; reflected in `docs/04-Concepts/architecture/bootstrap-portability.md` as the container-surface portability proof.
