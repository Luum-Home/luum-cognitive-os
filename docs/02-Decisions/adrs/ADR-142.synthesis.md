provenance: Cloud worker flows (ADR-137 Framing A) execute agent logic in ephemeral containers under human audit, and as soon as a flow writes code or reads project data, SOC 2/ISO 27001/GDPR become relevant — but three structural gaps existed: concurrent flows could write to the same Engram namespace/audit JSONL without per-flow attribution, air-gap deployment auditability was not explicitly committed despite the JSONL model already supporting it, and Engram observations could contain personal data (developer names, emails in code) with no documented erasure path.
---

## Decision
`.cognitive-os/runtime/agent-audit-trail.jsonl` becomes the single canonical, append-only compliance evidence surface that other per-domain JSONLs (`blast-radius.jsonl`, `hook-timing.jsonl`, etc.) join against. Every audit row from a cloud worker flow must carry `tenant_id` (`<flow_id>-<launch-timestamp>`, a stable compound key enforced server-side via `ENGRAM_CLOUD_ALLOWED_PROJECTS`) and `audit_class` (one of `access_control`, `change_management`, `availability`, `processing_integrity`, `confidentiality`, `privacy`, `sync` — each mapped to SOC 2/ISO 27001/GDPR clause references). Air-gapped deployments (no `ENGRAM_CLOUD_AUTOSYNC`, no external network calls) are formally classified as compliant, with a hard constraint that no audit row may require a network call to be produced — local JSONL first, network transmission is additive. GDPR erasure is a documented, operator-executed (not automated) procedure across local DB, git-jsonl export, and cloud sync, each erasure itself logged with `audit_class: privacy`. Schema extension to ADR-138's flow contract adds `tenant_id` and `audit_class` fields.

## Why
COS already produced significant audit signal (`agent-audit-trail.jsonl`, `blast-radius.jsonl`, `hook-timing.jsonl`, `clarification-events.jsonl`, `cost-events.jsonl`) but it wasn't bridged into a compliance-consumable shape — this ADR is explicit that it does *not* certify COS for any standard, only names the structural properties that make it "auditable towards" these regimes, with certification remaining an operator-level concern.

## Consequences
Positive: existing JSONL signal becomes compliance-queryable with just two added fields per row — no new infrastructure needed for air-gap; `tenant_id` closes the concurrent-flow attribution gap; GDPR erasure path is documented and auditable without COS needing to be a GDPR processor itself. Negative: schema change means pre-ADR rows lack the fields (migration convention: default to `maintainer` tenant / `change_management` class); SOC 2 Type II needs continuous evidence over 6-12 months and COS can't force operator discipline not to truncate the trail (mitigated, not solved, by `scripts/cos-audit-archive`); GDPR git-history erasure is irreversible and explicitly outside COS scope (operator uses `git filter-repo` or equivalent).

## Status & current state
Accepted, implemented. Implementation evidence: `docker/cos-worker/entrypoint.sh` — cloud-worker audit rows carry tenant_id/audit_class/credential source/billing identity; `scripts/cos-engram-cloud-enroll` and `scripts/engram-sync.sh` — sync rows use `audit_class: sync`; `scripts/cos-audit-archive` — compresses old rows into gzip archives without deleting/truncating source; `docs/04-Concepts/architecture/gdpr-erasure-procedure.md` — documented erasure workflow. Validated by `tests/unit/test_cos_engram_cloud_enroll_and_audit_archive.py` and `tests/audit/test_adr_139_141_142_cloud_surfaces.py`.
