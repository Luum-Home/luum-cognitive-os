## Decision
Separate remote ingress from provider/executor adapters as a hard architectural boundary. Remote ingress adapters (Telegram, REST, allowlist-based) may receive operator intent, normalize, rate-limit, and enqueue work — they do NOT own model credentials and do NOT execute project tools directly. Provider/executor adapters may invoke documented model/provider paths: official account-backed CLIs as black boxes, API-key/OAuth/device-login/provider-cloud flows, OpenAI-compatible gateways (OpenRouter/LiteLLM/local servers), local model runtimes (Ollama/LM Studio/llama.cpp/vLLM), or an explicitly-started and protected OpenCode headless server. No credential scraping is allowed anywhere: COS must not read vendor token stores, keychains, cookies, `~/.claude`, `~/.codex/auth.json`, or equivalent hidden auth files. Every provider/executor adapter must expose an `auth_probe` returning `ready`, `auth_required`, `unsupported`, or `unsafe`. The inventory lives in `manifests/remote-control-plane-alternatives.yaml`.

## Why
COS needed a governed way to be controlled when the operator isn't inside the current IDE and to connect to provider models/account-backed CLIs/API keys/local runtimes/chat surfaces, without turning every chat surface into a privileged executor or reinventing credential handling unsafely — the reviewed comparable projects made the ingress-vs-adapter split concrete and gave a license/proof-level baseline to inventory against.

## Consequences
Positive: COS can be controlled remotely without making every chat surface a privileged executor; provider/account support becomes adapter-scoped and testable; OpenCode can be evaluated as an executor without becoming a hard dependency; Telegram can start as a lab ingress adapter with strict pairing/allowlist and replay tests. Negative: more interfaces must be tested before remote autonomy is safe; a chat adapter that only enqueues work feels less "magical" than OpenClaw's direct execution; account-backed CLIs are economical for maintainers but not automatically safe for Docker/CI/hosted multi-tenant deployments; some comparable projects have blocked or review-required licenses, constraining code reuse even where concepts are useful.

## Status & current state
Status: implemented / "implemented for boundary/inventory scope" — the boundary, alternatives manifest, report, manual test, and contract tests exist, but concrete remote ingress/provider adapters remain follow-up implementation work (none are built yet). Verification: `tests/contracts/test_remote_control_plane_alternatives.py` (required manifest fields + core project coverage), plus `tests/audit/test_adr_contracts.py` and `test_adr_locations.py`. Rejected alternatives: cloning OpenClaw's full Gateway/channel model (too broad for COS's governance-first scope), letting Telegram directly run scripts/hooks (chat is untrusted ingress — must pass queue/lease/allowlist/redaction gates), reading existing CLI token files for convenience (violates the no-credential-scraping boundary), making OpenCode mandatory (COS must stay provider/harness agnostic), treating IDE projection as remote-runtime proof (structural files don't prove account-backed execution).
