## Decision
Adopt `manifests/task-lifecycle-schema.yaml` as the contract for COS task execution outside a single IDE session. It defines: task statuses from `queued` through `running`, `waiting_for_human`, `interrupted`, `resumable`, `pr_ready`, `approved`, `merged`, and terminal states; structured questions typed as `requirement`, `approval`, `credential`, `conflict`, `product_decision`, `clarification`, `review` (never hidden free-form chat); interruption records with reasons like `operator_interrupt`, `compaction`, `crash`, `auth_required`, `path_conflict`, `merge_conflict`, `policy_block`, and provider/rate/budget failures; append-only event communication for state/questions/leases/validation/PRs/completion; isolated worktree ownership at `.worktrees/{task_id}` with branch naming `codex/{task_id}-{slug}`; and a propose-only PR flow with required body sections that blocks direct publication actions.

## Why
Remote and IDE-driven work needed to share one lifecycle vocabulary so interruptions and agent questions become auditable and resumable, and so parallel agents can coordinate via claims/leases/worktrees/branch ownership instead of informal chat — this is a structural prerequisite for the eventual `cosd` daemon, testable before that daemon exists.

## Consequences
Positive: remote and IDE-driven work share the same lifecycle vocabulary; human interruptions and agent questions become auditable and resumable; parallel agents can coordinate through claims/leases/worktrees/branches; pull requests become the normal propose-only output for remote/headless work; the contract is testable ahead of a full `cosd` daemon. Negative: the first implementation needs additional queue/event plumbing before the protocol is fully enforced; small single-session tasks may feel heavier if forced through the full lifecycle prematurely; worktree cleanup must stay conservative to avoid deleting recoverable work; chat integrations need structured command/question handling before they're useful for complex builds.

## Status & current state
Status: implemented / implementation_status: partial — "implemented for contract scope; full queue/worker/PR runtime enforcement remains follow-up." The schema, contract tests, and manual proof checklist exist and are verified; direct publication actions are blocked at the contract level, but the runtime enforcement (queue, workers, PR automation) is not yet built. Verification: `tests/contracts/test_task_lifecycle_schema.py` (checks required states, transitions, fields, event types, worktree naming, blocked publication actions), plus `tests/audit/test_adr_contracts.py` and `test_adr_locations.py`.
