## Decision
The UI is four cooperating, independently opt-in surfaces, none mandatory: **Surface 1 — Operator CLI** (always-on; live operator state via scripts like `cos-boring-reliability`, `cos-doctrine-proposer`; structured JSON/text, pipes to jq); **Surface 2 — Phoenix** (opt-in; OpenTelemetry traces, latency, cost, eval scores; port 6006; governed by ADR-058); **Surface 3 — Engram Cloud** (opt-in; persistent cross-session memory, federation per ADR-136, BYOK activation per ADR-139); **Surface 4 — Obsidian/markdown reader** (opt-in, read-only; ADRs, doctrine docs, audit reports under `docs/`, git as audit trail). Cross-surface contract: no surface is required or canonical for everything; surfaces must not duplicate each other; no new web-dashboard code lands for governance/lifecycle/doctrine/audit_class/federation without a new ADR with a real driver, schema, and consumer.

## Why
Each artefact kind is genuinely best rendered on a different surface — live state is high-frequency and scriptable (CLI-shaped), traces are flame-graph/timeline-shaped (Phoenix-shaped, and an upstream OTEL-aligned tool already exists so building an alternative would be reinvention), persistent memory benefits from graph traversal and conflict resolution (Engram Cloud-shaped), and long-form decision text is best read in a markdown renderer with backlinks (Obsidian-shaped). Building a custom multi-pane dashboard embedding all of this would be a multi-sprint product effort duplicating what Phoenix and Obsidian already do well.

## Consequences
Positive: zero new web-dashboard code to maintain; maintenance load bounded to already-maintained/upstream-maintained surfaces; external buyers see four named, honestly-scoped activatable surfaces rather than one overclaimed "UI". Negative: cognitive load for new operators (must learn four surfaces exist, though Surface 1 alone suffices to start); discoverability gap (Phoenix/Engram Cloud URLs not surfaced from the CLI by default — planned follow-up footer); cross-surface state can be out of sync since each surface has its own freshness contract and none claims to be the single source of truth for cross-surface joins.

## Status & current state
Accepted; implementation_status: not-applicable (governance/doctrine ADR, evidence is a snapshot not a work item). ADR-170 superseded (its CLI-as-primary clause survives, generalized into Surface 1); ADR-169 unaffected. Implementation evidence snapshot at acceptance (2026-05-05): Surface 1 has 10 named CLI entry points in `scripts/`; Surface 2 activation exists via `requirements/dependency-lanes/observability.txt` (arize-phoenix); Surface 3 (Engram MCP tools work locally; cloud federation documented in ADR-136 but not activated by default — explicitly honest "not yet activated"); Surface 4 is `docs/` (172 ADRs at acceptance). Falsifiable claim: architecture holds for one year only if no surface drifts into another's territory, each stays one-command activatable, no external buyer demands a unified pane for 6 months, and the four surfaces continue covering all artefact-kind needs — otherwise revisit.
