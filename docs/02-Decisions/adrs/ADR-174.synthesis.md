## Decision
Add a `routing_patterns:` field to the SKILL.md frontmatter schema (list of `{pattern (regex, IGNORECASE), confidence (0.0-1.0)}`, English or Spanish). A new `_load_routing_from_frontmatter(skills_root)` scans `skills/`, `packages/*/skills/`, `.cognitive-os/skills/` for these declarations. `_build_default_routing_table()` merges frontmatter-derived entries with the legacy hand-coded fallback table, with frontmatter winning on conflict and orphaned hand-coded entries (no matching SKILL.md) triggering a stderr warning at instantiation. `tests/contracts/test_skill_router_coverage.py` enforces a non-regressing ratchet (currently 82 routed skills / 44.0% coverage floor) and `test_skill_router_invariant.py` proves the 5 proof-of-concept skills actually load their patterns from frontmatter.

## Why
The routing table was a hand-maintained second artifact that had to be kept in sync with SKILL.md files, and in practice that discipline was not maintained — every new skill required a manual router edit that frequently didn't happen. This follows prior art already established in this codebase: ADR-133 (auto-skill-generation: skills self-describe in frontmatter, generator derives from declaration) and ADR-064 (canonical hook registry: hooks self-describe). The cascading effect was that the orchestrator's `hooks/skill-router-prompt-suggest.sh` hook surfaced suggestions only as good as the (incomplete) routing table, so most skills were effectively invisible to auto-routing.

## Consequences
Positive: adding `routing_patterns:` to a skill's own frontmatter is now sufficient to make it routable — no second-file edit required; orphan warnings surface drift immediately without a dedicated audit script; the coverage ratchet prevents regression. Negative: skill authors must adopt the frontmatter discipline (a non-blocking validator hook reminds them); ~95 skills still needed migration at ADR acceptance time (estimated 2-4h via sonnet auto-extraction, tracked as a separate batch task); YAML-parsing 186+ SKILL.md files at router-construction time adds ~50-150ms overhead (acceptable for CLI use, cacheable if it becomes a bottleneck).

## Status & current state
Accepted, `implementation_status: implemented` for the core mechanism (frontmatter loader, merge/dedup logic, orphan warning, coverage ratchet, invariant tests) — 5 skills (`add-skill`, `audit-integrity`, `code-review`, `component-reality-check`, `cognitive-os-init`) migrated as proof-of-concept. Explicit remaining scope: batch migration of the ~103 remaining unmigrated skills is a separate follow-up task; a profile-aware routing refinement (so the metric reflects lean/standard/strict projection rather than every skill on disk) is noted as a needed follow-up; a falsifiable 90-day claim requires `SkillRouter().routing_entry_count / count_of_SKILL_md_files >= 0.95`, measured via `scripts/dogfood_score.py`'s `skill_coverage` dimension. A sibling ADR-174b (rules routing) is explicitly out of scope for this ADR.
