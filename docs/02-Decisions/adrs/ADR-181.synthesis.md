## Decision
A lightweight `AdrRouter` (`lib/adr_router.py`) indexes all non-tombstone/non-superseded/non-deprecated ADRs lazily, scoring keywords from three weighted tiers: frontmatter `tags:` (x3, curated/high-precision), title keywords (x2), and the first paragraph of `## Context` (x1, weak/broad). Score = `min(weighted_hits / sqrt(total_kw_count), 1.0)`. Public API `top_matches(prompt, n=3, min_confidence=0.85)` — deliberately a higher bar than the analogous skill/rule routers' 0.80, because false-positive ADR suggestions are judged more disruptive than false negatives. `hooks/adr-relevance-suggest.sh` (async `UserPromptSubmit`) calls this, always logs to `.cognitive-os/metrics/adr-suggestion.jsonl` for calibration, and emits an `additionalContext` hint like `"Relevant ADRs for this prompt: ADR-181 (..., 0.92)"` when matches clear the bar; killswitch `DISABLE_HOOK_ADR_RELEVANCE_SUGGEST=1`; latency budget <250ms. `manifests/adr-routing-coverage.yaml` tracks the baseline: only 43/180 (23.9%) non-tombstone ADRs had `tags:` at ADR time, against a 75% target (advisory, not enforced) — untagged ADRs degrade gracefully to title/context-only scoring.

## Why
This is explicitly the third instance of a pattern already proven for skills (ADR-174, frontmatter `routing_patterns:`) and rules (ADR-179, `rule_router.py`) — applying "declare-in-artifact routing" uniformly across all three primitive surfaces. ADRs got the lowest-priority, lightest-weight implementation of the three because they change at much lower frequency than skills/rules and have a smaller recall requirement — for ADRs specifically, a noisy false-positive suggestion is worse than silence, which drove the stricter 0.85 threshold and the choice of a cheap keyword-weighted scorer over full-text search (rejected: too many false positives, too slow for the 250ms budget) or an LLM-based selector (rejected: too expensive to run on every prompt).

## Consequences
Good: orchestrator gets passive ADR context hints with no manual lookup; unifies ADR/skill/rule surfaces under one routing pattern; low false-positive rate from the 0.85 threshold; the hook is async so it adds zero latency to the prompt round-trip. Accepted trade-offs: shallow tag-based matching means ADRs without good tags get poor suggestions, and tag quality varied widely (23.9% coverage at ADR time); the 0.85 threshold may prove too strict in the first 30 days, calibratable downward to 0.80 using the logged metrics once evidence accumulates; no deduplication across related ADR series (a tombstoned ADR and its successor can both score well on the same prompt), so the operator must read all suggestions before concluding one supersedes another.

## Status & current state
Accepted and implemented 2026-05-05. All three components (`lib/adr_router.py`, `hooks/adr-relevance-suggest.sh`, `manifests/adr-routing-coverage.yaml`) are shipped with unit tests in `tests/unit/test_adr_router.py` and `tests/unit/test_adr_relevance_hook.py`.
