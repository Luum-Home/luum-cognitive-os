## Decision
Introduce `cosd` — an opt-in, per-machine, long-running daemon that is the sole authoritative writer for critical surfaces: ADR sequence/ownership (number reservation, canonical filename, tombstone authorization/rejection), `manifests/agentic-primitive-registry.lock.yaml` mutations, `.claude/settings.json` regeneration, and release tag/version bumps. Sessions submit JSON "intent" files and poll for arbitrated JSON results; all other paths (skills, hooks, tests, reports) remain free-write, unaffected.

## Why
ADR-182 (branch ownership lock) and ADR-183 (cross-session event log) are peer-to-peer coordination — each session remains a sovereign writer. Some surfaces are too sensitive for any multi-writer pattern: a registry-lock race produces a corrupt lock, and that night's ADR-171/173/179 collisions demonstrated the concrete risk of naive sequential numbering under concurrency. Crucially, the incident was not only "two sessions picked the same number" — one session's tombstone rewrite erased active semantic ownership of an ADR, which is a distinct and worse failure mode that peer locks don't address. `cosd` generalizes ADR-163's instance-installer daemon role into a narrow single-writer authority for exactly these surfaces.

## Consequences
Positive: makes the ADR-171/173/179-style collision structurally impossible, eliminates the registry-lock race, and gives future federation (ADR-136) a natural integration point. Negative: ~2-4 weeks of new infrastructure, daemon process-management complexity (start/stop/restart/supervisor), added round-trip latency for arbitrated operations, and a new "must-be-running" primitive whose bypass (`COSD_BYPASS=1`) introduces an audit gap. Neutral: opt-in — most COS work doesn't touch daemon-arbitrated surfaces at all; without `cosd` running, sessions degrade to ADR-182/183/185 peer coordination.

## Status & current state
Accepted, `implementation_status: implemented` — first implementation landed as a local file-queue daemon scoped specifically to ADR identity arbitration (number request + tombstone request intent kinds), verified by an integration test asserting two competing intents get distinct numbers and a tombstone request for an active number is rejected. Broader responsibilities (registry-lock serialization, settings.json regeneration ownership, release/version bump ownership, cross-instance federation) remain declared in the ADR but not yet built — each requires its own intent kind with source-level proof and tests. Falsifiable claim: correct if, over a 180-day window, zero ADR-number collisions, zero registry-lock corruptions, zero settings.json regen races occur, and arbitration p99 latency stays under 200ms.
