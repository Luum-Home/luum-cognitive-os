## Decision
Model this as "harness action receipts" — a vendor-neutral event vocabulary (schema `harness-action-receipt.v1`) describing an action's source, repository context, evidence, and trust level, with VCS receipts (stage, commit, branch, push, PR creation, merge queue, bypass, conflict) as the first domain. Codex `::git-*{...}` directives are classified as harness directives, translatable into advisory receipts by an adapter — never treated as OS agentic primitives themselves. Four trust levels gate what a receipt can be used for: `advisory` (claimed, unverified — UI hints only), `observed` (local Git state confirms it — dashboards/warnings), `verified` (a governed hook/script checked it — event bus/policy reports), `authoritative` (merge queue or protected-branch landing confirmed it — task closure/release notes/strong audit).

## Why
The repo already has real Git safety primitives (`git-coop.sh`, `git-commit-scope-guard.sh`, `direct-main-guard.sh`, merge queue scripts, `git-context-capture.sh`, `event_bus.py`) but no vendor-neutral way to describe action reports coming from Codex, Claude Code, shell hooks, provider APIs, and merge queues while preserving trust boundaries. The missing piece was not another Codex-specific primitive — it was a receipt vocabulary that keeps harness UI protocol, actual Git mutation, and OS-governed enforcement as three distinct layers instead of conflating them.

## Consequences
Codex directives stay useful (UI hints, dashboards) without becoming architectural dependencies. Cognitive OS gains a portable action-telemetry vocabulary across harnesses. Existing Git safety primitives remain the sole enforcement layer — advisory receipts must never close tasks, satisfy high-stakes verification, or suppress collision warnings. Dashboards can distinguish advisory claims from verified/authoritative actions. Provider neutrality is preserved (GitHub-specific PR data is an adapter, not core schema).

## Status & current state
Partial, incremental. Implemented: `lib/harness_action_receipts.py` and `scripts/cos-action-receipt` validate schema, parse Codex directives, append JSONL to `.cognitive-os/metrics/vcs-actions.jsonl`, and promote advisory receipts to `observed`/`verified` via local Git evidence, pre-push checks, and provider API promotion. Best-effort receipt emission is integrated into `hooks/direct-main-guard.sh` (emits `vcs.push.blocked`, `vcs.bypass`), `hooks/git-commit-scope-guard.sh`, `hooks/git-context-capture.sh`, and `scripts/merge-to-main.sh`. Remaining (item 7 of the implementation plan): first-class provider adapters and direct `cos_lib.merge_queue` API emission. Runtime enforcement is explicitly unchanged — advisory receipts cannot satisfy safety gates, and existing Git primitives must never fail solely because receipt telemetry is unavailable.
