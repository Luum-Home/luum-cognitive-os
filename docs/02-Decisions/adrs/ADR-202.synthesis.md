## Decision
Define a private-content portability boundary orthogonal to public harness portability. Every private-content surface must declare one of 6 portability classes: `secret-never-touch` (never read/copied/exported/scanned except via an explicitly authorized secret API — .env, tokens, keys, certs), `local-only` (never leaves the project/workstation by automation — raw strategy, unredacted recovery artifacts), `same-user-harness` (may move between local harnesses for the same operator/machine — sanitized summaries, local skill state), `project-private` (shareable inside the same private repo boundary — reviewed ADRs, private plans), `sanitized-export` (may leave the project only after redaction/provenance checks — consumer evidence bundles), and `public`. Classification is explicit metadata, not inferred from file location — `.cognitive-os/strategy/` stays where it is but is now classified `local-only` by policy. `secret-never-touch` is stricter than `local-only`: excluded from generic grep, summarization, memory capture, metrics export, and classification scans by default; any access requires a secret-specific authorized API plus an immediate audit alert. Class transitions (e.g. `local-only → same-user-harness`) must be explicit gated events (operator approval, redaction proof, provenance record) — never silent metadata edits — and every projection/export/read of classified content writes an audit row to `.cognitive-os/metrics/private-content-access.jsonl`.

## Why
Public multi-tool support (ADR-008) answers how primitives project into different hosts; it does not answer which private content is safe to move between them. Without an explicit boundary, harness adapters and any future cloud/service runtime would have no rule preventing accidental leakage of raw strategy documents, unredacted recovery artifacts, or Engram memory across trust boundaries — the risk this ADR closes before treating cloud/headless service portability as safe by default.

## Consequences
Positive: multi-tool support becomes safe for private strategy and service runtimes; harness adapters gain a clear rule for what may be projected or retained; cloud/headless operation becomes auditable without leaking local operator state; router/maintainer-agent proposals can reason about content class before suggesting actions. Negative/trade-offs: new private-content surfaces need more metadata up front; some convenient cross-harness sync behavior is blocked until classified; existing docs/metrics surfaces need a classification audit sweep.

## Status & current state
Accepted, `implementation_status: implemented` per frontmatter, but the ADR's own status line qualifies this as "conservative manifest and audit substrate implemented" — i.e., Slice 2a (skeleton manifest with conservative defaults: known private roots as `local-only`, credential patterns as `secret-never-touch`) has landed; Slice 2b (justified elevations to less-restrictive classes with explicit redaction/provenance/retention justification) is ongoing follow-up work. Explicit open questions remain unresolved: Engram classification granularity (per observation/topic/namespace/bundle), GDPR/deletion-revocation workflows for hosted cosd/Engram Cloud, cross-machine same-user trust model, and a router intent classifier to distinguish "risk analysis mention" from "execution intent" (only a narrow `/auto-rollback` negative-context guard is implemented so far; the broader policy is deferred pending a fixture dataset).
