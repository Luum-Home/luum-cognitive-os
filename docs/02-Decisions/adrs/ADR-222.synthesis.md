## Decision
Replace speculative-capture-on-PreToolUse with a two-phase capture-then-commit pattern. Phase 1 (Plan, PreToolUse, after all blocking preflight passes): `pre-agent-snapshot.sh` computes the files that *would* be stashed and writes a capture plan to `.cognitive-os/runtime/pre-agent-plan-<agent_id>.json` — it does NOT call `git stash push` (verified as a read-only invariant: `git stash list` must be byte-identical before/after Phase 1). ADR-099's copy-on-untracked step still runs since it's non-mutating to git state. Phase 2 (Commit, agent launch confirmed): a new hook `hooks/agent-launch-confirmed.sh` fires only after the harness confirms the agent process is alive, reads the plan, runs the actual `git stash push`, resolves the SHA per ADR-221, and writes the v2 marker — it refuses to run without an existing plan file. Phase 3 (Restore, PostToolUse): unchanged behavior, but now tolerates plan-without-marker as a normal, silently-cleaned-up condition (preflight blocked, no stash was ever created — no orphan). For harnesses lacking a confirmed-launch signal, Phase 2 collapses into the PreToolUse path but only fires after a `dispatch-gate` lock (extending `validation-lock.sh`) confirms all preflight passed end-to-end.

## Why
Ordering alone (ADR-213's fix) is necessary but not sufficient: even with perfect ordering, a *different* downstream preflight hook (different concern, unrelated to `agent-prelaunch.sh`) can still block after the snapshot hook already ran and stashed. The real structural property needed is not "stash runs after preflight" but "stash never exists unless the agent actually launched." Rejected alternatives include: louder enforcement of ADR-213 ordering alone (insufficient, as above); running the snapshot hook at PostToolUse instead (too late — the agent has already mutated the working tree by then); a transactional git wrapper with auto-rollback (git has no native transaction primitive, and emulating one requires tracking the same SHA anyway with more code); and eliminating auto-stash entirely in favor of worktree-per-write-agent (acknowledged as "the right long-term move," but ADR-222 exists specifically to hold correctness while that larger migration — ADR-223 — is sequenced).

## Consequences
Positive: the 2026-05-06 orphan-stash bug class becomes structurally impossible — no stash exists if the agent never launched; ADR-213's previously-advisory ordering invariant gets actual CI enforcement via `tests/audit/test_pre_agent_hook_ordering.py` instead of living only as a header comment; the `COS_SUPPRESS_AGENT_SNAPSHOT` escape hatch becomes redundant for the "validation capsule mutates worktree" concern since there's no PreToolUse stash to suppress. Negative/trade-offs: one more hook in the lifecycle for harnesses with a confirmed-launch signal (mitigated — fallback mode uses no new hook, just a lock-extended single entry); harnesses without a confirmed-launch signal must use the lock-fallback path; a 5-minute plan TTL means a genuinely slow harness could lose its plan and have to re-plan (tunable via manifest); migrating existing in-flight v1 markers/plans piggybacks on ADR-221's one-cycle legacy reader.

## Status & current state
Accepted; Slices 1-8 implemented 2026-05-07 as an explicitly tactical mitigation while ADR-223 (worktree-per-write-agent) replaces operator-worktree auto-stash over the longer term. `manifests/pre-agent-snapshot.yaml` declares the two-phase contract; `hooks/pre-agent-snapshot.sh` now does Phase-1-only planning in non-legacy mode; `hooks/agent-launch-confirmed.sh` performs Phase 2 at the end of the `PreToolUse:Agent` chain; `hooks/post-agent-snapshot-restore.sh` treats plan-without-marker as normal cleanup; `hooks/session-start-stash-reapply.sh` sweeps stale plans at the 300s TTL from the manifest; hook ordering is registered across `settings.json`/`cognitive-os.yaml`/`manifests/hook-quality.yaml`. Tests cover unit (`test_pre_agent_two_phase.py`), audit (`test_pre_agent_hook_ordering.py`), and behavior (`test_pre_agent_blocked_preflight_no_orphan.py`) lanes. Remaining/deprecated: `COS_LEGACY_SNAPSHOT=1` still exists as an explicit opt-in to the old one-phase semantics. Investigation found Claude Code has no direct "confirmed launch" event (closest signal, the subagent's first tool-use, is too late), so Claude Code and any harness without explicit launch signaling use the lock-fallback path.
