## Decision
Treat holaOS as a **patterns-only reference library**: ideas, algorithms, policies, state machines, and taxonomies are freely adoptable (17 USC §102(b)); source code, identifiers, comments, fixtures, and documentation text are categorically blocked. Every adoption requires a mandatory three-role clean-room rewrite (research agent → implementer agent barred from holaOS paths → reviewer), a per-adoption ADR with `pattern_source` frontmatter and a 12-item compliance checklist, a specific commit-message template, and a triple audit trail (Engram observation, append-only adoptions registry, and a pre-commit `hooks/external-pattern-cleanroom-gate.sh`).

## Why
holaOS (Holaboss AI) is an Electron/TypeScript agent-computer platform that had already solved several problems luum-agent-os was actively working on — session-level memory governance, tool-replay budgeting, skill auto-evolution, context-reserve compaction, HMAC grants, proactive context bootstrapping. But its license (Apache 2.0 modified with BSL-like clauses) blocks hosted-service or commercially-embedded use of its source, with Holaboss able to tighten terms unilaterally. Under `rules/RULES-COMPACT.md` §10 `[license-policy]`, BSL-like licenses are BLOCK for code adoption. Rather than either ignoring ~10 identified high-value patterns or risking legal exposure through unconstrained copying, the project adopted a formal clean-room process modeled on the *Phoenix Technologies v. NEC* (1984) BIOS re-implementation precedent — the same doctrine that made independently re-derived object code from an abstract functional spec legally defensible.

## Consequences
Positive: unlocks roadmap acceleration from pre-digested pattern research without license exposure; the three-role separation plus append-only registry plus Engram trail creates a legally defensible chain of evidence; clear enforceable boundary against scope creep into code copying. Negative: meaningfully slower than copy-paste (research spec + implementer pass + reviewer + Engram + registry + gated commit per adoption); no ability to cherry-pick holaOS bugfixes; identifiers/module names must be independently re-derived, imposing cognitive overhead; a new adoption target with no existing annex needs a fresh research pass before implementation can start.

## Status & current state
Accepted, `implementation_status: partial`. The posture itself (patterns-only designation, clean-room protocol, per-adoption requirements) is canonized. Explicitly deferred as prerequisite infrastructure before ADR-260+ can be filed: the private holaOS adoptions registry, `hooks/external-pattern-cleanroom-gate.sh`, and the `adoption-from-holaos.template.md` ADR template. Two open legal questions remain unresolved and flagged for review before any SaaS/commercial-embed decision: jurisdictional scope of the "use the holaOS source code" restriction, and whether clean-room adoptions are protected from Holaboss's unilateral future license tightening.
