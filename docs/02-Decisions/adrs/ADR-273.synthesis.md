## Decision
Introduce one canonical pending-truth ledger with bilateral verification. A schema (`manifests/pending-truth.yaml`) gives every actionable item a stable composite id, a `type` (plan-checkbox/adr-slice/follow-up/user-request/audit-finding), a `source` file:line, a `status` (verified-pending/verified-done/ambiguous/obsolete/unverified), declared `evidence` checks, and a `next_action`. A read-only aggregator (`scripts/cos-pending-truth-aggregator`) walks the 5 source surfaces and emits normalized items plus `docs/06-Daily/reports/pending-truth-latest.{json,md}` — this Slice A commit implements only the schema and aggregator with 5 sample items. The 9 dispersed surfaces remain inputs, not replaced sources of truth: each preserves its own narrative role (plans explain "why," ADRs are architectural memory, the tracker orders by wave) while the ledger becomes the one operational answer to "is X pending."

## Why
No existing primitive actually solved this: `plan-claim-validator.sh` enforces verified proofs only on edit, doing nothing when code lands without touching the plan; `cos_session_backlog.py` aggregates but doesn't verify and was broken under Python 3.14 at the time; `cos-control-plane-audit` had no manifest covering plan items; and the other point-audits each covered only a slice (primitives, capabilities, feature claims) but not plan items or follow-ups. Root cause: plan checkboxes and ADR statuses are manually maintained by the author at write time, and nothing forces an update when code lands that closes the item.

## Consequences
Positive: one file (`pending-truth-latest.md`) answers "what is pending" without re-dispatching 3 Opus agents at ~$5/45min each; the bilateral-verification rule established here (code wins over paperwork when they disagree) becomes the precedent ADR-244's trust-score work draws on; drift becomes visible rather than silently compounding. Negative/tradeoff: until Slice C lands, closing a plan item still requires a manual edit that the ledger only picks up on next aggregation — the write-side gap this ADR names is not solved by this ADR itself. The ADR explicitly rejects eliminating the 9 surfaces (would lose sprint-planning context, decision rationale, and wave ordering) in favor of treating the ledger as strictly derived, not a replacement.

## Status & current state
Accepted. `classification_basis` and frontmatter state Slices A and B are implemented (schema + aggregator, and the verifier `cos-pending-truth-verify` — first run on 279 items found 7 verified-done, 267 verified-pending, 2 obsolete, 3 ambiguous), while Slice C (PostToolUse/Stop/PreCommit hook wiring) is designed and staged pending operator authorization via `COS_ALLOW_PROTECTED_CONFIG_WRITE=1`, since `protected-config-write-guard.sh` blocks agent-side writes to `hooks/`. Until Slice C activates, closing a ledger item is still a manual plan-checkbox edit.
