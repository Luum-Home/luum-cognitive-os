## Decision
Ship four orthogonal, additive Engram v3 capabilities, each independently adoptable without breaking the v2 surface: (1) evidence-grounded claims — new `evidence_sources`/`evidence_hashes` columns on `observations` plus a new `evidence_sources` table, with `validate_claim_evidence()` requiring non-empty evidence for claim-bearing types (`fact`, `decision`, `workflow`); (2) a dry-run/approved write gate (`lib/engram_write_gate.py`) that previews the exact payload before commit and can require explicit approval via `ENGRAM_REQUIRE_APPROVAL=1`; (3) a thin read-only BM25 retrieval wrapper (`lib/engram_fts5_search.py`) over the FTS5 index that already existed; (4) portable, SHA-256-integrity-checked bundle export/import (`lib/engram_bundle_exporter.py` / `_importer.py`).

## Why
Post-Wave-2 Engram already had FTS5 + BM25 and temporal validity scaffolding, but four concrete operational gaps remained unaddressed: claim-bearing observations (facts, decisions, architectural rules) had no machine-checkable link back to the artifacts that justified them, so a fabricated claim was indistinguishable from a verified one and source drift was undetectable; every `mem_save` was irrevocable with no preview mode, which mattered for high-blast-radius architecture-decision writes; BM25 scores and snippets existed in the database but were invisible to `lib.engram_client` and the HTTP daemon; and memory was bound to the local `~/.engram/engram.db` with no canonical, re-importable export for workstation moves (only a full SQLite copy or lossy Obsidian export existed).

## Consequences
Positive: claim-bearing observations become cryptographically anchored to sources so drift becomes detectable; dry-run previews unblock safe automation of high-blast-radius writes; BM25 becomes a first-class Python API without callers needing SQL; memory becomes portably cross-machine with integrity guarantees. Negative/accepted: four new modules (~1k LOC) to maintain; evidence sources are per-observation, so multi-observation claims sharing a source must manage de-dup externally (though the source table itself dedupes by `id`); `ENGRAM_REQUIRE_APPROVAL=1` could unexpectedly block hooks if enabled without care (mitigated by being off-by-default, opt-in per environment).

## Status & current state
Accepted, `implementation_status: implemented`, with strong verification (executing unit tests proving schema migration idempotency, evidence-hash determinism, write-gate dry-run non-persistence, BM25 ranking, and bundle export/import round-trip). Migration is fully additive/non-destructive across four phases (A: schema migration, B: opt-in evidence on writes, C: strict-mode env-gated enforcement off by default, D: optional future backfill of existing rows) — rollback is simply "stop using the new modules; columns remain NULL."
