## Decision
Adopt Graphify as a maintainer-only context optimization backend for an owned COS context-graph primitive, in controlled phases, treating Graphify as replaceable adapter machinery rather than the durable capability itself. COS will: keep Graphify output gitignored by default; use `scripts/cos-graphify-build` as the canonical build/update wrapper; expose usage via `skills/graphify-query/SKILL.md`; forbid upstream `graphify codex install`, hook installers, and platform installers in the normal workflow; treat Graphify output as navigation evidence, not proof (requiring source inspection or tests before implementation); require explicit approval before semantic documentation extraction or other large token-budget operations; join preload decisions with real session telemetry via `scripts/cos-graphify-run-telemetry` before making before/after token claims; and keep upstream web viewers, Neo4j export, watch mode, and MCP servers out of the default workflow unless separately approved.

## Why
Direct upstream IDE installation mutates persistent IDE state outside COS's primitive-projection model, so full adoption of Graphify's own installer path was rejected even though the local trial showed real navigation/context-reduction value for symbol-centered commands (`explain`, `path`, `affected`); broad natural-language `query` was found less reliable and kept secondary. Immediate semantic indexing of all docs/ADRs/rules/skills was deferred because the estimated first corpus was about 1,012,740 tokens before iterative updates — too large to run without an explicit budget gate.

## Consequences
Positive: maintainers get cheaper graph-backed context selection for code relationships without inheriting a visual graph product surface; adoption stays portable across IDE/CLI surfaces; generated artifacts don't pollute the repo by default; COS can add richer projection/hook behavior later without inheriting upstream installer assumptions. Negative: Graphify is not a full-repository optimizer or UI product by itself and needs scoped queries plus source confirmation; semantic documentation extraction has real token cost and stays gated; the first implementation is advisory/executable for maintainers only, not automatic lifecycle enforcement; real token-reduction claims need comparable before/after runs, and the telemetry joiner explicitly labels single-run evidence as non-causal.

## Status & current state
Accepted with partial implementation, verification_level: medium. Implemented: primitive shell, code-sliced Phase B baseline, Phase C hotspot reporting, Phase C.1 optimization targets, preload selector, token-footprint estimator, real-session telemetry joiner, controlled token-reduction smoke, real-context replay benchmark, Phase D semantic execution wrapper and backend receipt. Remaining, environment-dependent: rerunning semantic extraction once a backend is available, Codex TokenUsage normalization, and IDE/CLI projection beyond the maintainer skill. Six-phase plan: primitive shell → curated code graph baseline → hotspot/impact audit → optional semantic doc slices → real-session telemetry comparison → IDE/CLI projection.
