# ADR-341: Iroh Optional Transport Adapter

- Implementation status: partial
- Date: 2026-06-18
- Owner: Cognitive OS maintainers

## Status

Accepted. Iroh 1.0 is exposed as an OPTIONAL host tool with an OPTIONAL
transport adapter behind a feature flag; the default runtime path stays
Iroh-free and no Cognitive OS surface hard-depends on it.

## Context

Iroh 1.0 provides a stable peer-to-peer networking stack that dials peers by
public key, uses QUIC, performs NAT traversal where possible, and falls back to
relays when direct connectivity is unavailable. This is a good match for future
Cognitive OS use cases where two local-first agent runtimes should exchange
status without requiring a central server.

Cognitive OS must not make Iroh a mandatory dependency for consumer projects or
turn transport experiments into remote execution. The first slice therefore
needs an optional, disabled-by-default adapter contract that can be tested
locally without any destructive writes.

## Decision

Add Iroh as an optional transport adapter candidate, not a core runtime
dependency.

The initial adapter surface is:

- `scripts/cos-iroh-doctor`: reports optional Iroh readiness, relay mode,
  local keypair status, dependency availability, and local connectivity smoke.
- `scripts/cos-iroh-ping`: validates the COS peer-key ping contract. The current
  implementation includes a stdlib local-loopback backend for deterministic
  tests and does not claim real Iroh wire connectivity unless a future backend is
  promoted separately.
- `scripts/cos-agent-bus-iroh-adapter`: a minimal, append-only bridge for
  `heartbeat`, `status`, and `message` events. It rejects remote execution,
  destructive action words, and non-allowlisted peers.
- `scripts/cos_iroh.py`: shared Python implementation.

The adapter is disabled by default. Operators must explicitly enable it with
configuration or `COS_IROH_ENABLED=1`. Public relay use is not enabled by
default.

## Installation profile

`scripts/cos-deps-install.sh --profile iroh --dry-run` reports the optional
Iroh transport prerequisites. The profile includes `python3`, `cargo`, and an
`iroh` manifest entry. The `iroh` entry is intentionally manual/advisory until
COS promotes a concrete real-Iroh backend and supported install target.

`--profile full` also includes the `iroh` manifest entry so complete SO
dependency planning surfaces the optional transport, while the default profile
does not install or prompt for peer-to-peer transport tooling.

This preserves the claim boundary: local-loopback contract tests prove the COS
adapter safety envelope, not real Iroh wire connectivity.

## Non-goals

- No remote shell, command execution, file mutation, deployment, release, or git
  push over Iroh.
- No mandatory Iroh Python, Rust, Node, Swift, or Kotlin dependency in Cognitive
  OS installation.
- No product claim that the local-loopback contract is real Iroh wire transport.
- No automatic peer discovery. Peer allowlists are explicit public keys.

## Security model

The first slice only allows safe bus receipts:

- `heartbeat`
- `status`
- `message`

Every received peer key is parsed and checked against an allowlist when one is
configured. Destructive event types or message content are blocked before any
ledger write. The only write performed by the bus adapter is the local append-only
ledger at `.cognitive-os/iroh/agent-bus.jsonl`.

## Alternatives rejected

- **Ship Iroh as a required dependency** — rejected because it forces every
  consumer install to accept a substantial Rust runtime + relay-fallback
  behavior that most projects do not need; violates the ADR-093 default-lean
  install principle.
- **Custom WebRTC / raw QUIC transport** — rejected because it re-implements
  NAT traversal and relay fallback that Iroh already solves under a
  compatible license, with no differentiating capability we would gain.
- **Cloud-only relay (e.g., WebSocket to a hosted broker)** — rejected
  because it introduces a central-server dependency at odds with the
  local-first agent-runtime posture; kept as a future adapter alongside
  Iroh, not as a replacement.

## Consequences

Positive:

- Cognitive OS can evaluate Iroh-style peer transport locally without adding a
  hard dependency.
- Tests can exercise the protocol contract on laptops and CI without relays or
  internet access.
- Future real Iroh backend work has an explicit safety envelope and CLI shape.

Tradeoffs:

- The current backend is a local contract backend, not real Iroh wire transport.
- A second ADR/promotion is required before enabling real Iroh runtime behavior
  or public relays.
- Keypairs generated by this slice are local COS contract identities and must not
  be treated as real Iroh private keys.

## Verification

Targeted validation:

```bash
.venv/bin/python -m pytest tests/unit/test_cos_iroh.py tests/red_team/portability/test_cos_iroh_security.py -q
COS_IROH_INTEGRATION=1 .venv/bin/python -m pytest tests/integration/test_cos_iroh_local_endpoints.py -q
scripts/cos-iroh-doctor --project-dir "$(mktemp -d)" --init-keypair --self-test --json
scripts/cos-iroh-ping --self-test --json
scripts/cos-agent-bus-iroh-adapter --self-test --json
```

Required promotion evidence for a future real-Iroh backend:

1. Real Iroh dependency detection and version reporting.
2. Two local endpoints communicating through the selected Iroh language binding
   or binary.
3. Relay-mode tests for disabled, local, and public relay policy.
4. Security tests proving peer allowlist enforcement before message acceptance.
5. No remote execution or destructive writes.
