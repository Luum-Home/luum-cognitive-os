## What it is

A dated research report assessing Cognitive OS's agent-security posture by comparing its layered-hook approach against eight external sources (industry guidance on agent internet access, local shell execution, IDE-level file-deny controls, OWASP agentic-AI threat categories, MCP security best practices, and documented real-world exploit chains), producing a control matrix, numeric posture scorecard, and a P0/P1/P2/P3 prioritized backlog.

## Key mechanics

- **Executive framing**: the SO's posture is "governed and observable," not "cryptographically isolated" — in a fully-permissive local runtime, a malicious agent that disregards policy can still reach local files or run commands unless the underlying host runtime prevents it. The core achievement is converting many unsafe behaviors into governed, testable primitives; the core gap is that not all of those primitives are backed by an OS-level sandbox, egress policy, or committed IDE/agent-harness deny configuration.
- **External research synthesis** (8 numbered findings, each with an "implication for COS"): the "lethal trifecta" risk pattern (private data + untrusted input + outbound side effects combining dangerously) is directly applicable and the SO has a corresponding gate, but a fully-permissive runtime can still combine all three outside the hook path; cloud coding agents from other vendors disable outbound network access by default during agent phases, which the SO's local posture falls short of; unrestricted shell execution needs sandboxing or strict allow/deny lists, which two SO scripts satisfy but the broader `scripts/` surface does not; IDE-level settings support file-deny rules for sensitive paths but the SO's committed settings did not yet encode those denies at research time; OWASP's agentic-AI threat taxonomy (including "excessive agency") maps to many but not all SO controls; MCP integrations are a major control-plane risk (hidden instructions in third-party tool/server metadata, conversation-history exposure, insecure credential-adjacent storage, terminal-rendering deception); a documented real-world exploit chain shows adversarial input reaching an agent's local file writes to trigger code execution via MCP configuration files; recent academic work argues durable security requires architectural mitigations (least privilege, sandboxing, trust boundaries, integrity pins, observable audit) rather than filtering alone.
- **Control matrix** (10 risk rows x current controls/strength/gap): secret-file exposure (Medium — no OS-level filesystem deny in the runtime at research time), instruction injection via untrusted input (Medium — tooling exists but is optional/advisory), MCP-related poisoning (Medium-low — scanner exists but lacks trust-on-first-use pinning), unrestricted shell/process abuse (Medium — partial allowlisting only), runtime bypass flags (Medium), false-completion claims (High — strongest area), supply-chain risk (Medium), provider-dispatch abuse (Medium), long-lived memory poisoning (Medium), cost/DoS abuse (Medium).
- **Posture scorecard** (8 dimensions, 0-100): governance coverage 86, secret handling 72, MCP/tool safety 62, shell/process safety 58, auditability 78, test coverage 70, operational ergonomics 76, isolation strength 45 (flagged as "the critical weakness"). **Overall confidence: 68/100** for a fully-permissive local runtime; 80+/100 judged plausible if paired with deny settings, egress controls, MCP pinning, and a constrained runner for credential-bearing workflows.
- **Backlog with implementation status as of a 2026-05-05 follow-up**: P0 boundary-hardening items (committed file-deny settings, a protected-config-write guard, a network-egress guard, an MCP trust-on-first-use manifest) are reported as already implemented as repository contracts, hooks, and adversarial tests. P1 (dangerous-runtime-flag detection, a real no-network execution sandbox via container isolation, MCP tool-description hash drift detection, metrics-tamper detection, provider-spoofing detection) is also reported implemented with accompanying adversarial tests. Outstanding: P2 supply-chain/scanner-enforcement posture reporting and package-install provenance checks, and P3 mapping the internal red-team score to external threat taxonomies and generating a security-control ledger with trend tracking.
